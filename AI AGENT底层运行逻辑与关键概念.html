AI Agent 底层运行逻辑与关键概念

从感知到反思的完整闭环 · 核心概念逐个拆解 · 与对话模型及工作流的边界

如果说大语言模型是一颗会思考的大脑，那么 Agent 就是给这颗大脑装上五官、手脚、笔记本和一整套工作流程后形成的"能干活的系统"。本文先讲整体机制，再逐个拆零件。

一、整体机制：一个不停打转的循环

Agent 的工作方式不是"输入→输出"的一条直线，而是一个闭环。学界和工业界给它起了不少名字：agent loop、ReAct loop、think-act-observe cycle。剥掉术语，它就是下面这五步不断重复：

1 · 感知接收指令、环境状态、工具回执
2 · 规划把目标拆成可执行的步骤
3 · 调用输出结构化的工具调用意图
4 · 执行观察运行时真正执行并回收结果
5 · 反思迭代评估结果，改写计划或收工
类比：这像一个厨师做一道没做过的菜 —— 看冰箱里有什么（感知）→ 脑子里排个流程（规划）→ 让助手去拿酱油（调用）→ 尝一口汤（观察）→ 觉得太咸，加水还是换方案（反思）。

1. 感知输入 Perception

模型真正"看到"的东西，是一次调用时拼装出来的完整提示词，通常包含：系统提示词（角色、边界、输出规范）+ 工具 schema（有哪些工具、参数是什么）+ 召回的记忆 + 历史对话与中间步骤 + 当前用户输入与环境观测。

这一步定义了 Agent 的世界边界：没被喂进上下文的信息，对它而言不存在。

2. 任务规划 Planning

把模糊意图翻译成步骤序列。常见范式：

  • CoT（Chain of Thought）：先一步步写出推理再作答。
  • ReAct：Thought（思考）→ Action（行动）→ Observation（观察）循环交替，思考与行动互相校正。
  • ToT（Tree of Thoughts）：同时展开多条思路，评估后择优，必要时回溯。
  • Plan-and-Execute：先产出完整计划，再逐步执行，中途允许 replan。

子任务之间往往构成一张 DAG（有向无环图）：能并行的并行，有依赖的排队。

3. 工具调用 Tool / Function Calling

模型不执行任何代码。它输出的是一份结构化意图，例如：

{"name":"query_train","args":{"from":"北京","to":"上海","date":"2026-09-10"}}

随后由编排层（orchestrator / runtime）接手：校验参数 → 鉴权 → 在沙箱中真正调用 → 捕获超时与异常 → 返回结果。这个分工带来四个工程红利：可审计、可鉴权、可重试、可测试。

4. 执行与观察 Observation

工具回执（数据、报错、部分结果、环境变化）被写回上下文，成为下一轮推理的新证据。工程上必须做结果裁剪与截断——一次糟糕的 SQL 全表返回就能撑爆上下文。

5. 反思与终止 Reflection & Termination

判断"这一步有效吗、目标达成了吗、要不要换路"。终止条件通常是四选一：目标达成、步数预算耗尽、连续失败、需要人工确认（human-in-the-loop）。

二、核心概念逐个拆

2.1 规划与任务拆解

定义
将高层目标递归分解为可验证、可执行的原子子任务。
作用
降低单步难度、支持并行、让失败可定位到具体环节。
关键点
计划必须是"活的"——每次观察后都允许重写，僵化的计划是 Agent 失败的首要原因。
类比
总厨写菜单、排火候、分配灶台，而不是自己切所有的菜。

2.2 工具与函数调用

定义
用 JSON Schema 声明外部能力，由模型产出调用意图、由运行时执行。
作用
突破模型的两大天花板：知识截止时间，以及无法产生真实副作用（发邮件、下单、写库）。
关键点
工具描述写得越好，调用越准；工具数量过多会造成选择困难，通常需要分层或检索式挂载。
类比
大脑不下厨，只递出一张写清楚的点菜单。

2.3 记忆机制

模型本身无状态，Agent 的"记忆"全部由外部系统重建：

  • 工作记忆：上下文窗口内的内容。快、贵、容量有限、进程结束即失。
  • 长期记忆：向量库、关系库、文件。通过 embedding 语义检索按需召回，也存放用户画像与历史任务摘要。
  • 程序记忆：SOP、工具用法说明、成功过的执行轨迹库，相当于"肌肉记忆"。
类比：工作记忆是你此刻盯着的桌面，长期记忆是档案室，程序记忆是你不用想就会系鞋带的手感。

2.4 上下文管理

上下文是 Agent 最稀缺的资源。四板斧：

  1. 裁剪：丢弃过老的轮次与已失效的中间结果。
  2. 压缩：把长历史递归摘要成一段高信息密度的文字。
  3. 排序：重要信息放头尾（注意 lost-in-the-middle 效应，模型对中段记忆最弱）。
  4. 隔离：子任务交给子 Agent，各自持有独立上下文，只回传结论。

2.5 反思与自我修正

  • 单步反思：每步执行后即时自评有效性。
  • 轨迹级反思：失败后把原因写成自然语言"经验"存入记忆，下次同类任务先读经验（Reflexion 一类思路）。
  • 外部验证器：单元测试、规则校验、或另一个模型当裁判——比纯自我批评可靠得多。

2.6 多 Agent 协作

三种主流拓扑：

  • 流水线：调研 → 写作 → 审校，串行接力，适合可顺序拆分的任务。
  • 主从编排：一个 Orchestrator 分发子任务给多个并行 Worker，再汇总结果。
  • 圆桌评审：多角色（正方 / 反方 / 专家）围绕共享黑板产出，由仲裁者定稿，适合对抗式提质量。

协作依赖三件事：共享状态（黑板 / 工作区 / 数据库）、结构化消息协议、清晰的输出契约。代价是成本成倍上升、错误跨 Agent 传播、调试难度陡增。能用单 Agent 解决就不要上多 Agent。

三、三者之别

维度对话模型传统工作流AI Agent
驱动方式输入→输出预先画好的流程图目标驱动，运行时自主寻路
路径无路径概念完全确定，分支写死不确定，动态生成与重写
工具使用通常不能能，但调用点在编码期固定能，调用什么由模型决定
面对异常编造或道歉报错中断换工具、改参数、换路线
状态记忆会话内上下文外部状态机分层记忆 + 主动检索
适合场景问答、写作、解释高稳定强合规的固定流程路径未知的开放任务
一句话总结：工作流是铁轨，对话模型是播音员，Agent 是司机。铁轨不会错但去不了没轨道的地方；播音员能说会道但不动手；司机哪儿都能去，代价是偶尔走错路——所以你要给他地图（工具）、仪表盘（观察）和刹车（终止条件 + 人工介入）。

四、落地时的六个真实约束

  • 成本：一次任务可能触发几十次模型调用，预算控制与缓存是必修课。
  • 可靠性：错误会沿链路累积，需要重试、幂等、检查点与可回放的执行日志。
  • 安全：最小权限原则、工具白名单、沙箱执行、危险动作人工确认。
  • 可观测性：把思考轨迹与工具调用全部落盘，否则无法排查"它为什么这么做"。
  • 评估：不只看最终答案，还要看过程指标——步数、工具调用成功率、重试率。
  • 确定性边界：能用代码写死的流程就别让模型自由发挥，把不确定性关在最小笼子里。
